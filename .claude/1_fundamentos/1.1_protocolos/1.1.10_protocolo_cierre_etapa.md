# 1.1.10 PROTOCOLO: CIERRE DE ETAPA

**Tipo:** PROTOCOLO OBLIGATORIO  
**Nivel:** CRÍTICO - Sincronización trabajo  
**Aplicable a:** Cursor, Claude Code, Director  
**Última actualización:** 2026-06-10

---

## 🎯 DEFINICIÓN: ¿QUÉ ES "CERRAR ETAPA"?

Una etapa **NO** está cerrada cuando:
- ❌ Cursor dice "build OK" en cloud
- ❌ Claude dice "cambios aplicados"
- ❌ Hay cambios solo en local
- ❌ Hay cambios solo en cloud

Una etapa **SÍ** está cerrada cuando:
- ✅ Git tiene los cambios (fuente de verdad)
- ✅ Deploy verificado (Vercel/Streamlit)
- ✅ PC local sincronizado
- ✅ Director confirma visualmente

---

## 📋 LOS 5 PASOS OBLIGATORIOS

### **PASO 1: TRABAJO EN RAMA AISLADA** 🔨

**Responsable:** Cursor o Claude Code

**Acciones:**
```bash
# Crear rama específica
git checkout -b [tipo]/[nombre-descriptivo]

# Ejemplos:
git checkout -b cursor/niif-rimec
git checkout -b claude/fix-compra-ui
```

**Reglas:**
- ❌ NUNCA trabajar directo en `main`
- ✅ Una rama por tarea/etapa
- ✅ Nombre descriptivo (tipo/descripción)

**Estado:** TRABAJO EN PROGRESO

---

### **PASO 2: MOSTRAR PARA APROBACIÓN** 👀

**Responsable:** Cursor o Claude Code

**Acciones:**
```bash
# Generar evidencia
git status --short
git diff --stat
git diff [archivo-crítico] | head -100

# Build verification
npm run build  # o comando relevante
```

**Entregar al Director:**
```markdown
## PROPUESTA DE CAMBIOS - [NOMBRE ETAPA]

**Rama:** [nombre-rama]
**Archivos modificados:** [cantidad]
**Tipo:** [feat/fix/refactor/docs]

### Cambios aplicados:
[Lista detallada]

### Evidencia:
- git status: [output]
- git diff --stat: [output]
- Build: [✅ OK / ❌ FALLÓ]

### Vista previa:
[Screenshot o descripción visual si aplica]

**Estado:** PENDIENTE APROBACIÓN
```

**Reglas:**
- ❌ NO declarar "ETAPA CERRADA"
- ❌ NO declarar "COMPLETADO"
- ✅ Declarar "PROPUESTA" o "PENDIENTE APROBACIÓN"
- ✅ Mostrar evidencia real (git diff, build)

**Estado:** PENDIENTE APROBACIÓN

---

### **PASO 3: GIT COMMIT Y PUSH** 📤

**Responsable:** Cursor o Claude Code  
**Requiere:** ✅ Aprobación explícita del Director

**Solo ejecutar si Director dice:**
- "Aprobado"
- "Autorizá"
- "Subilo"
- "Push"

**Acciones:**
```bash
# Commit
git add [archivos-modificados]
git commit -m "[tipo]([scope]): [descripción]

[Detalles si necesario]

Co-Authored-By: [Agente] <email>"

# Push
git push origin [nombre-rama]

# Reportar
echo "✅ Pusheado a rama: [nombre-rama]"
echo "Commit: $(git rev-parse HEAD)"
```

**Formato commit:**
```
feat(niif): Migrar RIMEC a tema claro institucional

- Fondos oscuros → celeste NIIF (#f1f5f9)
- Texto blanco → oscuro legible
- Cards oscuras → blancas con sombra
- Azul institucional RIMEC (#002B4E)

Co-Authored-By: Cursor <cursor@example.com>
```

**Reglas:**
- ❌ NO pushear sin aprobación
- ✅ Commit descriptivo
- ✅ Reportar nombre de rama y commit hash

**Estado:** EN GIT (fuente de verdad)

---

### **PASO 4: DEPLOY Y VERIFICACIÓN** 🚀

**Responsable:** Claude Code (orquesta)  
**Ejecutores:** Vercel/Streamlit (automático)

**Acciones:**

#### **4A: Integración a main (si aprobado para producción)**
```bash
git checkout main
git merge [nombre-rama] --no-ff
git push origin main
```

#### **4B: Verificar deploy**
```bash
# Vercel (rimec-web, report)
# Deploy automático en push a main
# Verificar: https://[proyecto].vercel.app

# Streamlit (control_central)
# Requiere restart manual si es local
# O redeploy si es cloud
```

#### **4C: Verificación funcional**
- Abrir URL de producción
- Verificar cambio visible
- Screenshot de confirmación

**Reglas:**
- ✅ Esperar a que deploy complete (Vercel ~1-2 min)
- ✅ Verificar visualmente en producción
- ✅ Screenshot como evidencia

**Estado:** DESPLEGADO EN PRODUCCIÓN

---

### **PASO 5: SINCRONIZAR PC LOCAL** 💻

**Responsable:** Claude Code  
**Requiere:** Deploy verificado

**Acciones:**
```bash
# En PC del Director (C:\Users\hecto\Nexus_Core\[proyecto])
git fetch origin
git checkout main
git pull origin main

# Verificar
git log -1  # Ver último commit
git status  # Debe estar limpio

# Confirmar
echo "PC local sincronizado con:"
echo "Commit: $(git rev-parse HEAD)"
echo "Rama: $(git branch --show-current)"
```

**Entregar al Director:**
```markdown
## SINCRONIZACIÓN PC LOCAL

✅ Git pull completado
✅ Commit: [hash]
✅ Archivos actualizados: [cantidad]

**Verificación:**
- PC local = mismo commit que producción
- git status limpio
- Listo para próxima etapa
```

**Reglas:**
- ✅ Confirmar que PC tiene MISMO commit que producción
- ✅ Verificar git status limpio
- ✅ Reportar al Director

**Estado:** PC LOCAL SINCRONIZADO

---

## ✅ VERIFICACIÓN FINAL: ETAPA CERRADA

**Una etapa está CERRADA solo cuando:**

```
✅ PASO 1: Rama creada y trabajo hecho
✅ PASO 2: Director aprobó cambios
✅ PASO 3: Git tiene los cambios (commit + push)
✅ PASO 4: Deploy verificado en producción
✅ PASO 5: PC local sincronizado (mismo commit)
```

**Reporte de cierre:**
```markdown
## ✅ ETAPA CERRADA: [NOMBRE]

**Rama:** [nombre-rama] → main
**Commit:** [hash]
**Deploy:** [URL] ✅
**PC local:** Sincronizado ✅

**Próxima etapa:** [nombre] o NINGUNO
```

## 👥 ROLES Y RESPONSABILIDADES

### **CURSOR**
**Puede:**
- ✅ Crear ramas
- ✅ Modificar código
- ✅ Hacer commit local
- ✅ Push a rama (después de aprobación)
- ✅ Generar evidencia (diff, build)

**NO puede:**
- ❌ Declarar etapa cerrada por su cuenta
- ❌ Push a main sin autorización
- ❌ Modificar PC local del Director directamente

**Debe reportar:**
- Estado: PROPUESTA/PENDIENTE
- Evidencia: git diff, build
- Solicitar: Aprobación explícita

---

### **CLAUDE CODE**
**Puede:**
- ✅ Crear ramas
- ✅ Modificar código (PC local)
- ✅ Merge a main (después de aprobación)
- ✅ Pull en PC local
- ✅ Orquestar workflow completo

**NO puede:**
- ❌ Declarar etapa cerrada sin los 5 pasos
- ❌ Deploy sin verificar
- ❌ Merge sin aprobación

**Debe reportar:**
- Estado de cada paso
- Confirmación de sincronización
- Cierre formal de etapa

---

### **DIRECTOR (Héctor)**
**Decide:**
- ✅ Aprobar o rechazar propuestas
- ✅ Cuándo hacer deploy
- ✅ Cuándo cerrar etapa

**Verifica:**
- ✅ Cambios visualmente
- ✅ Funcionalidad en producción
- ✅ PC local sincronizado

**Da feedback:**
- Aprueba: "Aprobado", "Subilo", "Push"
- Rechaza: "No", "Cambiá X", "Ajustá Y"

## ⚠️ ANTI-PATRONES (NO HACER)

### ❌ **Anti-patrón 1: "Completado" sin Git**
```
Cursor: "Build OK, cambios aplicados, COMPLETADO ✅"
Realidad: Cambios solo en cloud, git vacío
Problema: NO está en PC del Director
```

**Correcto:**
```
Cursor: "Build OK en cloud, PROPUESTA lista para aprobación"
Espera aprobación → push a git → entonces sí avanza
```

---

### ❌ **Anti-patrón 2: Push sin Aprobación**
```
Cursor: *hace cambios y pushea directo*
Problema: Director no vio/aprobó
```

**Correcto:**
```
Cursor: Muestra diff → espera "Aprobado" → entonces pushea
```

---

### ❌ **Anti-patrón 3: "Cerrado" sin PC Sincronizado**
```
Claude: "Deploy OK, etapa cerrada ✅"
Realidad: PC local no tiene los cambios
Problema: Director no puede continuar trabajo
```

**Correcto:**
```
Claude: Deploy OK → pull en PC local → verifica → entonces "cerrado"
```

## 📏 CHECKLIST DE CIERRE

**Antes de declarar ETAPA CERRADA, verificar:**

```
[ ] Rama creada con nombre correcto
[ ] Código modificado y guardado
[ ] Build exitoso
[ ] git diff muestra cambios
[ ] Director vio y aprobó
[ ] git commit ejecutado
[ ] git push ejecutado
[ ] Rama reportada a Director
[ ] Merge a main (si aprobado)
[ ] Deploy verificado en producción
[ ] URL producción funciona correctamente
[ ] git pull en PC local ejecutado
[ ] PC local tiene mismo commit que producción
[ ] git status limpio en PC local
[ ] Director confirma que ve cambios en PC
```

**Solo si TODOS son ✅ → ETAPA CERRADA**

---

## 🎯 REGLA DE ORO

> **"Una etapa NO está cerrada hasta que el Director pueda ver los cambios en su PC y en producción al mismo tiempo"**

**Corolario:**
- Si solo está en cloud Cursor → NO cerrada
- Si solo está en PC local → NO cerrada
- Si solo está en Git → NO cerrada
- Si Git + Deploy + PC sincronizado → **✅ CERRADA**
