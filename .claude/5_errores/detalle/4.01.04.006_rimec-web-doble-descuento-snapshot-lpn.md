## Causa raíz (dos fallos encadenados)

### A · F5 resetea % (pre_autorizado ignorado)

`asegurarFacturasDescuentosLote` en cada GET sesión descartaba match FI si divergía el dictado Report y **reaplicaba** el % predeterminado (~20 %), pisando la edición del vendedor.

### B · Doble aplicación de descuento (montos)

1. Tras **Guardar descuentos** / validar, `carrito_item.precio_snapshot` = **neto** (una cascada sobre LPN/LPC).
2. Al hidratar (`itemFromBD`), el snapshot neto se copiaba a **`precio_lpn` / `precio_base`**.
3. `fragmentarCarrito` tomaba ese valor como **bruto de lista** y aplicaba otra vez `precioNetoCascada`.
4. Patrón numérico típico en FI ya confirmada:  
   `neto_ok = cascada(bruto, d_FI)` · `snap ≈ cascada(neto_ok, [20])` → etiqueta **DOBLE_20**.

**No es un bug de “654 vs 638” en semántica de tallas.** Es un bug de **capas de precio** (lista vs neto) que **sí pegó a líneas 654** en el pedido auditado.

## Fix código (anti-réplica / anti-propagación)

| Archivo | Regla |
|---------|--------|
| `rimec-web/store/sesionVenta.ts` · `itemFromBD` | LPN/LPC **solo** desde stock. **Prohibido** rellenar LPN con `precio_snapshot`. `precio_base` = bruto lista; `precio_snapshot_neto` = neto BD. |
| `fragmentarCarrito` | Cascada **una vez** sobre bruto lista. Si solo hay snapshot neto (post Guardar), **no** re-descontar. |
| `asegurarFacturasDescuentosLote.ts` | Si `pre_autorizado` + descuento comercial real → **congelar** match (no reset F5 a 20 %). |
| `carritoDescuentosFi.ts` | Guardar no regenera lote si ya existe FI. |

**Ley invariante:** `precio_snapshot` post-guardar = **NETO**. `lpn`/`lpc*` = **BRUTO**. Nunca intercambiar.
