# 4.02.03.010 · Admin IC — botón verde no recalcula FI existentes

**Código índice:** `4.02.03.010`  
**App:** Report · **Módulo:** Pedido proveedor · tab **Administrador IC** · botón verde lote FI  
**Estado:** 🟡 **PARCIAL** · hotfix deploy `442ec81` 2026-07-12 · PP-0015 FI regeneradas (12)  
**Severidad:** **GRAVE** — FI obsoletas en producción tras corrección caso/biblioteca/PELE  
**Caso real:** PP-2026-0015 (`pedido_proveedor.id=15`) · cliente **2894** · DIAZ E HIJOS  

---

## Síntoma

Tras corregir casos comerciales (biblioteca BCL → PELE) y recalcular **prefacturas** en Administrador IC, las **facturas internas ya creadas** conservan montos, SKUs y agrupación **viejos**.

### Evidencia PP-0015 · shop 2894

| Capa | PROMOCIONAL 300 p | BR-VZ 840 p |
|------|-------------------|-------------|
| **PF (derecha Admin IC)** | Gs. 38.724.000 | Gs. 125.755.200 |
| **FI 15-PV008 (tab FI)** | — | Gs. **126.566.712** con desc. (95 SKUs · 1.140 p) — **no coincide** |
| **IC (izquierda)** | monto desactualizado | monto desactualizado |

El Director ve PF correctas post-corrección pero FI/PDF siguen con precios del lote **anterior**.

---

## Causa raíz (error de principiante — agente + código)

### 1 · API `generar-fi-lote` — atajo `already_done`

```typescript
if (nFiExistentes === nEsperadas) {
  return { ok: true, already_done: true, ... }; // ⛔ NO recalcula
}
```

Si el **conteo** IC=FI cuadra, el backend **asume** lote válido aunque PF/FI **montos** hayan cambiado.

### 2 · API — omite IC con FI previa

```typescript
if ((fiIcRows[0]?.c ?? 0) > 0) { omitidas++; continue; }
```

Solo crea FI **faltantes**; nunca **reescribe** las existentes.

### 3 · UI — `loteExacto` bloquea el botón verde

Cuando `nFi === nIc` y Chusa N1, el botón verde pasa a **«Ver resultado»** y **no llama** a la API (`generarFiLote` retorna en `loteExacto`).

### 4 · Reparación agente incompleta

Scripts `repair_programado_retroactivo` / `reemparejar_casos_pf_programado` regeneraron FI en **algunos** PP vía motor batch, **sin** garantizar paridad Admin IC ↔ PF por shop/caso. PP-15 quedó con **10 FI** desalineadas vs **12 PF** (Chusa N1 ❌).

---

## Ley operativa (Director · 2026-07-12)

> **Administrador IC manda.**  
> Al pulsar el **botón verde**, el sistema **debe** borrar todas las FI **RESERVADA** del PP y **rehacerlas todas** desde la proforma/prefactura **actual**, **sin excepción**.  
> Si hubo corrección en casos, biblioteca, PELE o import — **no** basta con contar FI; hay que **recalcular montos**.

Aplica a **todo PP PROGRAMADO** (`categoria_id=3`).

---

## Comportamiento canónico (post-fix)

| Paso | Acción |
|------|--------|
| 1 | `loadAdministradorIcPp` — PF actuales desde PELE/biblioteca |
| 2 | `borrarFiReservadasProgramado(ppId)` — solo RESERVADA · bloquear si CONFIRMADA |
| 3 | Generar **N FI** = parejas Chusa (o motor programado si Chusa N1 falla y Director ordena) |
| 4 | Verificar montos PF ↔ FI por shop/caso antes de cerrar |

**Prohibido:** `already_done` · skip IC con FI · UI «Ver resultado» sin recalcular tras cambio de caso.
