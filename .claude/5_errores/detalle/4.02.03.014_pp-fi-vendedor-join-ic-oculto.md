# 4.02.03.014 · PP detalle FI — vendedor oculto (join IC erróneo)

**Código índice:** `4.02.03.014`  
**App:** Report · **Módulo:** Pedido proveedor → tab Facturas Internas  
**Ruta:** `/proceso-importacion/pedido-proveedor/[ppId]?tab=fi`  
**Keyword registro:** **Documenta** (Director 2026-07-19)  
**Estado:** ✅ **RESUELTO local 2026-07-19**

---

## Síntoma

En PP **ABIERTO** (caso real **PP-2026-0006**), la cabecera FI mostraba **Vendedor: —** aunque en BD `factura_interna.vendedor_id` apuntaba a un registro válido de **`vendedor_v2`** (ej. GIANINA, FRANCIS, EDUARDO).

El campo **Creador** del PP mostraba **ADMINISTRACION** (desde `intencion_compra.id_vendedor`), distinto del vendedor comercial grabado en la FI tras generación / recálculo.

Impacto: Logística OK, PDF FI y bandeja gerencial sin nombre de vendedor; imposible corregir desde tab FI en época de pruebas.

---

## Causa raíz

`listFacturasInternasPp` (`detail-query.ts`) resolvía el nombre del vendedor **solo** vía `LATERAL` sobre IC con condición:

```sql
AND ic.id_vendedor = fi.vendedor_id
```

Cuando la IC seguía con vendedor genérico (**ADMINISTRACION** = id 1) pero la FI ya tenía el vendedor comercial real (ids 7, 9, 10…), el join lateral **no matcheaba** y el UI mostraba **—**.

Mismo patrón en `fi-pdf-data.ts` (PDF FI tab PP).

---

## Corrección

| Pieza | Cambio |
|-------|--------|
| `detail-query.ts` | Nombre desde `fi.vendedor_id` → `vendedor_v2`; fallback IC; quitar filtro `ic.id_vendedor = fi.vendedor_id` del lateral |
| `fi-pdf-data.ts` | Mismo criterio para PDF |
| `fi-pp-actions.ts` | `actualizarVendedorFiDesdePp` — PATCH vendedor en FI + IC (mismo cliente/PP) + pendiente logística |
| API | `PATCH …/fi/[fiId]/vendedor` |
| `PpFiCard.tsx` | Select **vendedor_v2** editable mientras PP no esté ENVIADO |

**Regla operativa:** vendedor canónico en PP/FI = **`vendedor_v2.id_vendedor`** en `factura_interna.vendedor_id`. Editable con PP abierto (igual que LP/plazo en cabecera IC).
